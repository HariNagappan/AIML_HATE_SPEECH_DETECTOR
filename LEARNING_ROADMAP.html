Learning roadmap: from scratch to understanding this project end to end

Ten phases, ordered so that no phase ever needs a concept from a later one. Python · numpy · PyTorch · Transformers · FastAPI · explainability

Measured facts about the size of this project, so you can calibrate: 52 Python files / 5,987 lines in backend/app; 18 test files (149 passing, 47.7 s); 9 files that define an nn.Module; exactly 1 file that uses autograd; 47 TypeScript files / 4,303 lines in the frontend (which this roadmap ignores — it's a separate skill).

So: you are not learning 6,000 lines. You are learning about 25 concepts and then watching them get arranged in one particular way.

Read this first: three truths that change how you study this

1. The project reuses ~25 concepts, not ~200

Almost every file is a permutation of the same small set: a dataclass, an nn.Module, a forward(), a config lookup, a try/except. Learn the set once and the codebase becomes readable in an afternoon.

2. You only need calculus intuition, not calculus

Autograd computes every derivative for you. You need to know what a gradient is and why averaging over a path beats one sample at a point. That's it. No proofs, no chain-rule grinding by hand.

3. BERT is a downloaded object, not something you build

You write AutoModel.from_pretrained("bert-base-uncased") and get 111.5 M trained parameters. Everything you author sits around it.

The 4-layer spine — the mental model to build toward

Everything in this roadmap exists to make these four layers obvious to you. If you can explain this diagram out loud, you understand the project.

  LAYER 1 · DATA          "what shape is a training example?"
     UnifiedExample { current_text, context_text, hate/target/reason labels, rationale }
     key idea: None means "we were not told". It does NOT mean "none".
                                    │
  LAYER 2 · MODEL         "how do texts become a prediction?"   (needs Phase 2 + 3)
     shared BERT → E_c, E_p → |Ec-Ep|, Ec⊙Ep → [4×768] → Linear → 1024 → heads → logits
     key idea: the SAME weights encode both texts, so their vectors are comparable.
                                    │
  LAYER 3 · TRAINING      "how does it get good?"               (needs Phase 4 + 5)
     masked multi-task loss (-100 = skip) + InfoNCE; one missing label must never
     become a fake label.
                                    │
  LAYER 4 · EXPLANATION   "why did it say that?"                (needs Phase 6 + 7)
     Integrated Gradients → token scores → merged spans w/ char offsets
     → deterministic templates → JSON. No LLM writes a single word.

0Phase 0 — the Python gap (1–2 weeks)

This is the phase people skip and then drown in Phase 2. Do not skip it.

Diagnosis, from your machine: you have Python 3.14 with torch 2.14.1+cpu installed globally, but python is not on your shell PATH, and the project's pytest runs are fighting Windows temp-folder permissions. None of that is a knowledge gap — it's an environment gap, and it will waste hours if you don't fix it first.

Step 0.1 — fix the environment (do this today)

  • Install Python 3.11 or 3.12 (not 3.14) — matching backend/README.md's "Python 3.11+". Newer isn't better here: wheel availability for torch/transformers is.
  • Put it on PATH (tick "Add python.exe to PATH" in the installer).
  • Learn virtual environments properly: python -m venv .venv → activate → pip install -r requirements.txt. One environment per project, always.
  • Run the suite with an explicit temp dir: python -m pytest -q --basetemp=.pytest-tmp. You should see 149 passed, 2 skipped. That green run is your baseline sanity check for the rest of this roadmap.

Step 0.2 — the Python that this codebase actually uses

Not "all of Python". This list, verified by grepping the repo:

  • Type hints everywhere — Optional[str], List[Dict[str, Any]], -> returns. Read them as documentation; they're half the readability.
  • Dataclasses — @dataclass class UnifiedExample. Auto-generated __init__. Used in 9 files. Learn field(default_factory=list).
  • Pydantic v2 BaseModel — runtime validation of API bodies. Different thing from a dataclass: it checks at runtime.
  • Decorators — @property, @classmethod, @staticmethod, @lru_cache, @contextmanager, @field_validator, @torch.no_grad(), @dataclass. Five of these appear in this project; meet them early.
  • Optional / narrowing — you will constantly see if x is not None:. Understand why: missing annotation ≠ absent value.
  • Function-local imports — import torch inside a function, not at the top. Used deliberately to keep imports cheap. Learn why.
  • Context managers — with open(...), with torch.no_grad():, with torch.autocast(...).
  • Generators / yield — appears once, in the FastAPI lifespan. Recognise it, don't master it.
  • *args / **kwargs — model(**kwargs) is everywhere. Know the unpacking operator cold.
You're done with Phase 0 when: the test suite runs green from a clean venv, and you can read backend/app/datasets/unified.py top to bottom without looking anything up.

Resources: the official Python tutorial (sections 4–9), then Real Python on dataclasses, type hints, and decorators. Skip anything about metaclasses, async internals, or packaging. Not used here.

1Phase 1 — the maths that matters (1–2 weeks, intuition only)

You need to know what these objects mean and why they're shaped that way. You do not need to compute any of them by hand.

Vector and matrix basics unlocks 60% of the code

A vector is a list of numbers. 768 numbers = a "768-dimensional vector". The project's whole representation story is: text → vector such that similar meanings are near each other.

Four operations are load-bearing. Learn these four and nothing else:

OperationWhere it appearsPlain meaning
Concatenation [a; b][E_c; E_p; D; M] → 3072Stick two lists end to end. 768+768+768+768 = 3072.
Dot product a·bevery nn.Linear, cosine similarityMultiply matching slots, add them up. One number: "how aligned are these two?"
Matrix multiplyLinear(3072→1024)3072 numbers in, 1024 out, via a 1024×3072 grid of learned weights. This is the fundamental layer.
Element-wise product / abs-diff a⊙b, |a−b|M and D in the interaction blockSlot-by-slot comparison. "Where do these agree?" / "where do they differ?"

Probability, softmax and cross-entropy

  • Softmax — turns arbitrary scores [3.2, −1.1, 0.4] into probabilities that sum to 1: [0.87, 0.02, 0.11]. That's the entire content of softmax_head.py.
  • Cross-entropy — a penalty for "how surprised were you by the truth?" If the true class had probability 0.87, penalty is small. If it had 0.02, penalty is large. This is the classification loss here.
  • BCE (binary cross-entropy) — the same idea for a yes/no question; used by the evidence head, one yes/no per token.
  • Sigmoid — squashes one score into a 0–1 probability. Used when there's only one output.
  • Temperature — dividing scores before softmax. Low temperature (0.07 here) makes the biggest score dominate hard. Learn what that does to the contrastive loss and why it matters.

Gradients — the one idea that unlocks Phase 2, 4 and 6

Intuition only. A gradient answers: "if I nudge this one number slightly, which way does the error move, and how much?" That's a slope. Training walks downhill along slopes. Attribution (Phase 6) reads the slopes to ask "which input words moved the answer?"

Chain rule, understood not computed: when you stack layers, gradients flow backwards through each one, each multiplying by its local slope. loss.backward() does this for 113 M parameters in one call. That's why nobody computes derivatives by hand here.

One number you must understand deeply: cosine similarity

It measures the angle between two vectors, ignoring their lengths, giving a score from −1 to 1. It is used by the contrastive loss. Crucially, it's why vectors are L2-normalised first in contrastive.py — dividing by length so only direction matters. One line, one concept, load-bearing.

You're done with Phase 1 when: you can look at nn.Linear(3072, 1024) and say out loud — "3072 numbers in, multiplied by a learned 1024×3072 grid of weights plus a bias of 1024, giving 1024 numbers out, and that grid holds 3,146,752 learnable values."

2Phase 2 — PyTorch mechanics (2–3 weeks: the big one)

This is the single highest-leverage phase. Nine files in this repo define an nn.Module, and every one of them follows the same three-step pattern.

Step 2.1 — the nn.Module pattern (learn this once, recognise it 9 times)

class ContextInteraction(nn.Module):
    def __init__(self, ...):                    # 1. declare the learnable pieces
        super().__init__()                      #    (must come first — sets up internals)
        self.projection = nn.Linear(3072, 1024)
        self.dropout = nn.Dropout(0.2)

    def forward(self, e_c, e_p):                # 2. define the maths, tensors in → tensors out
        raw = torch.cat([e_c, e_p, d, m], dim=-1)
        return self.dropout(self.activation(self.projection(raw)))

    # 3. nn.Module automatically gives you .parameters(), .to(device), .train(), .eval()

That auto-magic third point is the payoff: you never write code to move the model to a GPU, to iterate its weights, or to switch dropout off. The framework does it because you inherited from nn.Module and stored layers as self.something.

Step 2.2 — tensors and shapes where beginners actually get stuck

A tensor is a multi-dimensional array that can run on a GPU and track gradients. Three habits:

  • Always know your shapes. [B, T, H] = batch size, sequence length, hidden size. [B, K] = batch, number of classes. Print x.shape constantly. Every bug in this project is a shape bug or a mask bug.
  • Batch dimension first, always. Even for one request — that's why inference.py builds tensors of batch size 1.
  • Broadcasting: e_p * mask.unsqueeze(-1) in full_model.py takes a [B] mask and stretches it across 768 slots. unsqueeze(-1) adds a dimension; view, reshape, cat, permute are the other four you'll meet.

Step 2.3 — autograd, the training loop, and the five things people miscount

optimizer.zero_grad()          # 1. clear old slopes (they ACCUMULATE by default)
outputs = model(**batch)       # 2. forward
loss = criterion(outputs, y)   # 3. measure wrongness
loss.backward()                # 4. autograd fills .grad on every parameter
optimizer.step()               # 5. nudge every parameter downhill

Now layer the real-world complications, which trainer.py uses all of:

ConceptOne-line explanationWhere in the repo
AdamWThe optimizer. A smarter downhill walker that keeps per-parameter momentum. lr=2e-5 is deliberately tiny so fine-tuning doesn't wreck pretrained knowledge.trainer.py
LR scheduler + warmupStart with a near-zero learning rate and ramp up, then decay. Prevents a violent first few steps._linear_warmup_decay()
Gradient accumulationRun several small batches, only step after collecting all their slopes. Fakes a big batch within small memory.grad_accum_steps
Gradient clippingCap slope size so one weird batch can't blow up the run.clip_grad_norm_
AMP / mixed precisionMost arithmetic in 16-bit. ~2× faster on GPU. Needs a GradScaler to stop small numbers underflowing.build_grad_scaler()

no_grad() / detach()Stop tracking gradients when you're only predicting. Saves memory and time.all inference paths

ReproducibilitySeed random, numpy, torch, torch.cuda — all four, or your runs differ.set_seed()

Step 2.4 — the -100 masking trick read this file twice

Read app/training/losses.py once you understand cross-entropy. It's short and it contains the project's honesty rule in code form: -100 means "this example has no label for this task", PyTorch skips those rows, and if the whole batch is -100 the loss is None and the component is dropped from the sum.

You're done with Phase 2 when: you can write a small nn.Module from scratch, train it on toy data in a 20-line loop with AdamW, and explain why optimizer.zero_grad() must be called. Then read app/models/context_interaction.py and follow every line.

Resources: the official PyTorch "Learn the Basics" 60-minute blitz, then the entire "Training a Classifier" tutorial typed out by hand (not copied). That single exercise covers 80% of Phase 2.

3Phase 3 — Transformers and how BERT works (2 weeks)

Goal: read a sentence, and picture the tensors flowing through BERT. Not memorise the paper.

The concepts, in dependency order

  1. Word embeddings — each word-piece id maps to a learned 768-vector.
  2. Position embeddings — added so the model knows word order. note this one
  3. Token-type embeddings — for two-sequence inputs. note this one
  4. Self-attention — every token computes "how much should I look at every other token?" This is what makes meaning context-dependent.
  5. Multi-head — 12 attention patterns in parallel, different ones picking up different relationships.
  6. Feed-forward + residual + LayerNorm — the per-layer machinery. Recognise the names; you won't modify them.
  7. Encoder vs decoder — BERT is encoder-only. No text generation. That's why this project needs no LLM.
  8. [CLS] and [SEP] — the two special tokens. [CLS]'s output vector summarises the sentence.
  9. Tokenization / word-pieces — the ## prefix rule. Learn AutoTokenizer and return_offsets_mapping=True.
  10. Pretraining vs fine-tuning — from_pretrained() loads 111.5 M already-trained parameters; you then nudge them for your task.
  11. Freezing — setting requires_grad=False. Three modes in bert_encoder.py: full / frozen / partial.
  12. Truncation & padding + attention masks — max_seq_length=128 truncates; padding fills the batch; the mask tells attention to ignore the filler. mask bugs are everywhere

What you must be able to do by the end

from transformers import AutoTokenizer, AutoModel
import torch

tok = AutoTokenizer.from_pretrained("bert-base-uncased")
model = AutoModel.from_pretrained("bert-base-uncased")
model.eval()

enc = tok("They should all be kicked out.",
          return_tensors="pt")
out = model(**enc)

print(enc["input_ids"].shape)     # [1, T]
print(out.last_hidden_state.shape)  # [1, T, 768]  per-token
print(out.last_hidden_state[:, 0].shape)  # [1, 768] the [CLS] vector

# what the tokenizer actually did:
print(tok.convert_ids_to_tokens(enc["input_ids"][0]))

Then inspect the model's own embedding module: model.embeddings — find where word, position and token-type embeddings get added. That single line is the crux of the biggest bug in this repo (see trap #1).

You're done with Phase 3 when: you can run the snippet above, explain every shape in the output, and answer: "why do we use the [CLS] vector instead of averaging all token vectors?" Then read app/models/bert_encoder.py (169 lines) and follow it completely.

Resources: the Hugging Face "Transformers" course chapters 1–3. Then Jay Alammar's "The Illustrated Transformer". Then read the project's own backend/README.md "Why BERT" and "Why is the encoder shared?" sections — you'll actually understand them now.

4Phase 4 — multi-task learning and the head pattern (3–4 days)

Small phase, huge payoff: it explains why the model has four heads and why the API is full of *_available flags.

  • One body, many mouths. A shared representation (the 1024-vector) feeds several small task-specific classifiers. The body learns general understanding; each mouth answers one question.
  • Why share? Related tasks regularise each other — learning "who is targeted" helps learn "is this hateful". And you compute the expensive BERT pass once.
  • Loss weighting. λ_hate, λ_target, λ_reason: one loss per task, added with weights. Ask why contrastive is 0.5 while the others are 1.0.
  • Missing labels — the central practical problem of multi-task learning. Datasets annotate different things. If you Naively fill gaps with 0, you teach the model that everything is class 0. Hence -100.
  • trained_heads as a derived fact. The trainer records which losses actually fired. That set is written to the checkpoint and read back by the API — so "available" is never hand-maintained and can never drift from reality.
You're done when: you can explain why a Counter-Context training batch produces a hate_loss and a contrastive_loss but no target_loss, and why the served checkpoint contains no target_head keys at all.

5Phase 5 — contrastive learning (1 week)

The idea: teach by comparison rather than by labels alone.

The plain-English version. Take a comment C and its real preceding comment P1. The model's context-aware representation should look similar to the comment-only anchor. Now staple C to a wrong comment P2 — the representation should look different. Train until the true pairing beats the false one.

Why bother? Without this, the network can cheerfully ignore the context input entirely and still score well, because the comment alone often predicts the label. This loss is the pressure that forces it to actually use context. It is the mechanism behind the project's entire "context matters" claim.

What to actually learn

  • Positive / negative / anchor — the three roles in every contrastive setup.
  • Cosine similarity + L2 normalisation — from Phase 1, now used for real.
  • InfoNCE — the specific loss formula. Read it as: "softmax over similarities, and I want the positive to win." F.cross_entropy with the target always being index 0 is a neat trick worth noticing.
  • Temperature — 0.07 sharpens the distribution. Ask what happens at 1.0 vs 0.01.
  • How many negatives? InfoNCE's power comes from many negatives. This repo defaults to 1, and there's a second subtle problem: the negative sampler is a random.Random inside collate_fn, which runs in parallel DataLoader worker processes.
  • Train-only components — the projection layer exists but is never used at inference. Learn to spot that pattern; it wastes ~328 K parameters in the shipped file.
You're done when: you can explain why a batch with only 1 negative gives a weak learning signal, and describe what you'd change to fix it. (You'll need this for Phase 10.)

6Phase 6 — explainability and Integrated Gradients (1–2 weeks)

This is the intellectual heart of the project. It's also the phase where the biggest risk lives — so learn it properly, not superficially.

Step 6.1 — the family of methods

MethodWhat it isWhy it's not used here
Attention weightsLook at where the model attendedAttention ≠ explanation. Widely regarded as misleading. The repo explicitly refuses to do this.
Supervised rationaleTrain a head to predict human highlightsImplemented (evidence_head.py) but needs gold annotations and is a different technique — compared experimentally, not used for the UI.

Step 6.2 — Integrated Gradients, properly understood

Sundararajan, Taly & Sundararajan (2017). The recipe:

  1. Pick a baseline — "no information". Here it's the PAD embedding.
  2. Draw a straight line from baseline to the real input's number-vectors.
  3. Sample points along that line (default 32 steps).
  4. At each point, ask "how sensitive is the output to each input slot?"
  5. Average those sensitivities, then multiply by (real_input − baseline).

Result: one signed score per token. Positive = pushed the prediction up. Negative = pushed it down. The "multiply by difference" step is why IG satisfies the completeness axiom (the scores add up to the output change) — and why it's more faithful than raw gradients.

Step 6.3 — why this needs inputs_embeds, and the trap

You cannot interpolate between integer token IDs — halfway between word 1045 and word 2033 is meaningless. So IG must work in continuous space: the embedding vectors. That's why attribution.py builds embeddings itself and passes them via current_inputs_embeds.

The trap, stated plainly. BERT's embedding module does three things: look up the word vector, add a position vector, and add a token-type vector. If you hand BERT raw inputs_embeds and it does not re-add positions and token types, then IG is explaining a slightly different function than the one that produced the label — and the evidence section is subtly unsound.

This is the #1 thing to verify in the whole repository. The test is a numeric parity check: same input, forward-twice-both-ways, assert the predictions match. Learn enough to write that test.

Step 6.4 — evidence extraction and the honesty discipline

  • Scores → threshold (relative, 0.15 × strongest) → merge adjacent → decode subwords → top-k. That's evidence_extractor.py.
  • Relative vs absolute thresholds: a low-confidence prediction still gets some evidence. Ask whether that's honest or misleading — a good discussion to have with yourself.
  • Character offsets — return_offsets_mapping=True gives you where each token sits in the original string. This is what the frontend highlights. It removes an entire class of mis-highlighting bugs.
  • Template composition vs generation. The explanations are built from fixed templates grounded in real model outputs. Learn to see this as an engineering choice about trust, not a limitation.
  • Abstention as a feature. When the context layer can't establish a relationship, it says so. A system that always produces confident reasoning is a system you can't trust.
You're done when: you can explain the completeness axiom in one sentence, explain why gradients alone are misleading, and describe what a parity test would check.

8Phase 8 — data engineering (1 week)

Unglamorous, and the place where projects quietly fail. This repo handles it well and there's a lot to copy.

  • The adapter pattern — one module per dataset, both emitting one shared dataclass. Never merge raw data.
  • None is a first-class value. target_label: null means "not annotated"; "none" means "annotated as no target". Conflating them trains the model on false negatives. This distinction is the spine of the whole data layer.
  • Preserve, don't guess. Unmapped label values go into metadata rather than being force-fitted into a canonical bucket.
  • Label mapping as its own layer — dataset quirks → canonical categories, so the model never sees raw corpus weirdness.
  • Word-level → subword alignment — human highlights are per-word, BERT works in word-pieces. align_rationales_to_subwords() is the bridge. Think hard about what happens to the [CLS]/[SEP] positions (they get -100).
  • Honest splits — this repo uses random splits, which leaks near-duplicate tweets between train and test. Learn why that inflates metrics; it's one of the fixes in Phase 10.
  • JSONL as the interchange format — one JSON object per line, streamable, diffable, greppable. A good default for ML pipelines.
  • Spot the naming quirk in Counter Context: the field called target is the current comment, and context is the preceding one. It has nothing to do with target groups. Always verify field semantics against the paper — this is a real transferable lesson.

9Phase 9 — evaluation and ablations (1 week)

This is what separates a project from a demo. Without it, "we added context" is just an assertion.

  • Accuracy lies on imbalanced data. If 90% of examples are "normal", a model that always says "normal" scores 0.90. That's why macro-F1 is the selection metric here.
  • Precision / recall / F1 — know which one matters when. And macro vs weighted averaging.
  • Confusion matrix — where do errors go? Offensive↔hate confusion is the expected failure mode of this task.
  • ROC-AUC — threshold-independent quality, for the 2-class case.
  • Train/val/test discipline — the test set is read once. Early stopping and model selection use validation only. This repo does this correctly; notice it.
  • Ablation methodology — the six experiments in ablation.py: baseline → +context → +interaction → +contrastive → full multi-task → +evidence. Each step removes exactly one thing. Learn to design a study where every claim has a controlled comparison behind it.
  • Honest reporting. The current served checkpoint's best validation macro-F1 is 0.566 over 3 classes (chance ≈ 0.33), selected at epoch 2 of 4 with validation loss rising afterwards. That's overfitting on a small dataset — not a working detector. Learn to write that sentence about your own work without flinching.
You're done when: you can explain why macro-F1 above accuracy, and why "epoch 2 of 4" is a more interesting fact than the architecture diagram.

10Phase 10 — rebuild it yourself, smaller (3–4 weeks)

You don't understand an architecture until you've rebuilt a working version of it. Do it tiny and offline — no downloads, no GPU, minutes not hours.

The exercise: a miniature version of this exact project

Dataset:      200 tiny toy sentences you write yourself
Encoder:      YOUR OWN 2-layer transformer, or a random-init tiny BERT
              (hidden_size 64, 2 layers, 4 heads — fast enough to iterate in seconds)
Interaction:  D = |E_c − E_p|, M = E_c ⊙ E_p, [E_c;E_p;D;M] → Linear → 64
Heads:        hate (3 classes) + target (3 classes)
Loss:         masked multi-task, with -100 for missing labels
Evidence:     Integrated Gradients over YOUR model's embeddings
Serving:      FastAPI, one endpoint, model loaded via lifespan
Tests:        one unit test per component

Build it in this order, and stop to run a test after each step. If you can build this, you can read every file in this repository with confidence — because you'll have made the same decisions in miniature and felt where the difficulty actually is.

Then, the harder follow-ups (in order of payoff)

  1. Write the IG parity test for the real project (Phase 6, Step 6.3). Highest value single action available to you.
  2. Run the real ablation study (scripts/evaluate.py / ablation.py) and write up what actually changed between experiments.
  3. Fix one real gap end to end — e.g. raise negatives_per_anchor to 4–8, construct hard negatives from the same label neighbourhood, and measure whether macro-F1 moves. Report the result either way.
  4. Serve a passing-checkpoint model — train the full multi-task config, export a serving checkpoint, point default.json at it, and see the UI light up sections that were previously hidden.

The 7 traps: things in this codebase that require extra care

Each of these is a place where a plausible-looking implementation has a subtle problem. If you learn to reason about these seven, you've learned to think like an ML engineer, not just a coder.

#TrapWhat it teaches youPhase
1IG embedding path may skip position/token-type embeddingsThe most important lesson in the repo: an explanation is only valid if it explains the same function that made the prediction. Verify with a numeric parity test.6
2Missing label (None) vs negative label ("none")Data semantics are the foundation. A single conflated None can corrupt an entire training run silently.8
3InfoNCE with 1 negative, sampled in a parallel workerA loss can be present in the code, logged in the metrics, and still teach the model almost nothing. Always ask "how much signal is actually here?"5
4Random splits on duplicate-heavy social dataLeakage inflates metrics. The number can be technically correct and practically meaningless.9
5encode_pair with input_ids=None → uncaught ValueErrorCatching RuntimeError but not ValueError at an API boundary means a 500 instead of a clean 503. Error mapping is part of the design.7
6model_info() assumes model.hate_head existsThe baseline model names it classifier. Any place that reaches into an object by attribute name is a place that breaks when the object changes shape.7
7A keyword list decides how the decision is describedA deterministic explainer is far better than an LLM — but it's still a second, unevaluated decision-maker in front of your evaluated one. Know where your system's "voice" comes from.6
