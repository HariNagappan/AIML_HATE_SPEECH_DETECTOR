Solid Backend Architecture & The Learnables

Context-Aware Hate Speech Detection with Structured Evidence-Based Reasoning — explained from first principles, in plain English. Backend only. Everything here is verified against the actual code in backend/app/.

How to read this document. Every section starts with a green In plain English box — read those and you'll understand the system. The detail underneath is there when you want to go deeper. Words in orange are analogies; words in code style are real file or variable names. One recurring word to know up front: "learnable" simply means a part of the model whose numbers (weights) change during training. Parts that never change during training (calculators, templates, rules) are not learnable — and this project is unusually honest about that split.

0The whole thing in one page

In plain English: You send the API two sentences — a comment, and (optionally) the comment that came before it. The backend answers five questions and shows its work: WHAT was said (hateful? offensive? normal?), WHO it targets (a religion? a nationality? nobody?), WHY it's harmful (a threat? an insult? exclusion?), WHICH WORDS triggered the decision (highlighted phrases, copied verbatim from your input), and DID CONTEXT MATTER (was the previous comment actually used?). The crucial design rule: the system never makes anything up. If a part isn't trained, the API says "not available" instead of guessing. Explanations are assembled from real values like a form being filled in — no chatbot writes them.

The learnable side is a shared trunk with specialist branches (one detective gathers the evidence; several specialists each give their verdict from the same case file). The non-learnable side is a transparency layer that explains the verdict using only real inputs and real scores.

1Seven first principles

Every design decision in this codebase traces back to one of these. If you understand these seven, the whole architecture becomes obvious rather than memorized.

1 · Meaning depends on context

Principle: "They should all be kicked out" is only fully interpretable if you know what "They" refers to. So the model must genuinely read the previous comment — not as a display gimmick.

Consequence: two encoding passes, an interaction module that mathematically combines the two, and a training game (contrastive learning) that rewards using context correctly.

2 · One shared brain, not two

Principle: the current comment and the previous comment are encoded by the same BERT weights (full_model.py calls the same self.encoder twice).

Consequence: both summaries (E_c, E_p) live in the same "language", so comparing them (|E_c − E_p|, E_c ⊙ E_p) is meaningful. Two separately trained encoders would produce two incomparable dialects. Bonus: half the memory, and both passes train the same weights.

3 · One dossier, many specialists (multi-task learning)

Principle: hate / target / reason are related questions about the same comment, so they share one representation instead of three separate models.

Consequence: each extra task acts as free practice for the shared trunk (studying for three related exams makes you better at each one) — and the whole thing is one deployment instead of three.

4 · Trust must be earned, verbatim

Principle: evidence for a decision must be actual phrases from the input, with exact character positions — computed by a principled attribution method (Integrated Gradients), never by attention weights relabeled as "explanations", never generated text.

Consequence: the reasoning/ package is a separate, non-learnable layer; every evidence span carries start/end offsets so the UI can highlight the exact words.

5 · No fake supervision, no fake answers

Principle: a head trains only on data that genuinely has its label; a head that has no trained weights reports available: false.

Consequence: missing labels are encoded as -100 and the loss skips them; untrained heads return null; the reason head stays dark until someone supplies real reason annotations. This is why the system can't hallucinate.

6 · Configuration over hard-coding

Principle: no model name, dimension, threshold, label list or loss weight is baked into classes. Runtime comes from .env → core/config.py; training comes from configs/*.yaml → training/configs.py.

Consequence: every component is a switch (use_context, use_contrastive, use_reason…), which is exactly what makes the ablation experiments (§12) possible.

7 · Fail soft, degrade loudly

Principle: a subsystem failing must never take the whole request down — but it must never fail silently either.

Consequence: if the model isn't loaded, /health stays up and prediction returns 503; if the reasoning builder crashes, you still get the classification with "summary": "Reasoning unavailable." and the error is logged.

2The layer map

In plain English: the backend is organized like a restaurant. The pantry (data layer) preps ingredients. The kitchen (model + training) does the actual cooking. The food critic (evaluation) scores dishes. The explainer at the table (reasoning layer) describes what you're eating. The waiter (API/serving) takes orders and plates the result. Each floor only talks to its neighbours — that's what makes it "solid".

The dependency rule that keeps it solid

Arrows only point downward. The model layer doesn't know FastAPI exists. The training loop doesn't know about the API. The reasoning layer reads the model but changes nothing. That's why you can train on a laptop script, serve in Docker, and test offline — the layers never reach into each other's business.

4The Learnables — every knob the model can turn

In plain English: a neural network is a giant panel of numbered dials ("weights"). Training =nudging millions of dials, bit by bit, until the outputs look right. A learnable component is any part of the panel that gets nudged. Below is the complete panel of this project — every dial-group, its size, which "teacher" (loss) nudges it, and when it's allowed to learn. Think of it as the model's org chart: who works here, how big is their desk, and who signs their performance review.

Read the table like an investor

99.5% of the capacity is the pretrained BERT trunk — knowledge it already brought from reading billions of words. The project-specific additions are tiny: ~3.5M knobs ≈ 3% of the total. That's the whole point of fine-tuning (hiring a seasoned detective and giving them a one-week briefing on this specific beat, instead of raising a detective from birth).

4.2 · Each learnable, from first principles

1 · The BERT encoder — the shared reader ~109.5M

Plain: BERT is a pretrained text reader. Feed it a sentence and it outputs two useful things: a summary vector (the [CLS] slot — one row of 768 numbers that "stands for" the whole sentence) and a per-word vector for every token, where each word's vector already knows about its neighbours (in "kick the bucket", the vector for "bucket" is bucket-the-idiom, not bucket-the-object).

The dials inside:

  • Word-lookup table (embeddings): 30,522 words × 768 numbers ≈ 23.4M — each word's "starting meaning"
  • Position table: 512 positions × 768 ≈ 0.39M — so "dog bites man" ≠ "man bites dog"
  • 12 transformer layers: ≈ 7.09M each ≈ 85.1M — each layer lets every word look at every other word (attention) and refine its meaning (feed-forward network: 768→3072→768)
  • Pooler: ≈ 0.59M — polishes the summary vector

The three freeze modes (set in configs/*.yaml):

  • full — all 109M dials nudge during training (best quality, most compute)
  • frozen — BERT is a read-only oracle; only the small heads learn (fast experiments, cheap)
  • partial — freeze the word-lookup + bottom frozen_layers (default 4); let the upper, more abstract layers adapt (keep the intern's vocabulary, retrain their judgement)

Why shared matters (again): full_model.py encodes the current and previous comment with the same self.encoder. Same dials → same "dialect" → the comparison math in the next component is meaningful.

2 · Context Interaction — the "how do these relate?" module ~3.1M

Plain: you have two summary vectors, each 768 numbers. How do you combine them so a small classifier can use them? This module concatenates four signals and squeezes them through one learnable layer:

E_int = [ E_c ; E_p ; |E_c − E_p| ; E_c ⊙ E_p ] → Linear(3072 → 1024) → GELU → Dropout
  • E_c ; E_p — "what each comment says" (the raw summaries)
  • |E_c − E_p| — "how different they are", dimension by dimension. Big values where the two comments disagree (like holding two transparencies up to the light and marking where they don't overlap)
  • E_c ⊙ E_p (element-wise product) — "where they agree / reinforce each other": two large same-sign numbers multiply to something big; anything else shrinks toward zero

Why engineered features at all? A plain concatenation (the simple mode) forces the linear layer to discover subtraction and multiplication from scratch. Handing it those two comparisons ready-made is a 3-line head start — and the ablation ladder (§12, exp2 vs exp3) exists precisely to test whether this head start helps.

Fallback rule: no previous comment → E_p becomes a zero vector (D = |E_c|, M = 0), and the API reports context_used: false. One code path, no special cases.

3–5 · The three verdict heads ~3–9K each

Plain: each head is one small layer that reads the shared dossier (1,024 numbers) and emits one score per answer option. Softmax turns scores into probabilities that sum to 1. These are the smallest learnables — and the ones the user actually sees.

  • Hate head → {hate, offensive, normal}. Also has an opt-in binary mode (one score + sigmoid + threshold) that must be configured explicitly — labels are never silently collapsed (principle 5: no quiet relabeling).
  • Target head → 9 categories (race, ethnicity, nationality, religion, gender, sexual_orientation, political_group, other, none). Trained only where the dataset annotates targets.
  • Reason head → 8 categories (insult, dehumanization, negative_stereotyping, threat, exclusion, discrimination, incitement_to_violence, other). It is a learned classifier — not a keyword lookup — and stays dark until someone supplies real reason annotations via scripts/import_reason_annotations.py. No annotations → no training → reason_available: false in the API. This is principle 5 in its purest form.

First principle — why heads share one dossier: every extra task forces the trunk to build more general features. The target question ("is a group mentioned?") genuinely helps the hate question ("is that group attacked?"). Multi-task = free cross-training.

6 · The evidence head — the highlighter in training 769

Plain: a one-layer token classifier: for each word vector (768 numbers) it outputs a single 0-to-1 "is this word part of the harmful part?" score. It learns from HateXplain's annotator highlights (humans marked which words are rationales) after those word-level marks are aligned onto subword tokens (tokenizer.align_rationales_to_subwords — every subword piece inherits its parent word's mark).

Important family distinction: this head is supervised prediction — a student that practices highlighting against an answer key. The Integrated-Gradients method in the reasoning layer (§9) is post-hoc attribution — an x-ray taken after the fact. Different techniques; the project ships both and compares them (ablation exp6). At serving time, the evidence you see in the UI comes from the x-ray (IG), not this head.

Wiring detail worth noticing: this head reads the encoder's token states directly (768-dim), not the 1,024-dim dossier. So its gradient flows into BERT but never through the interaction module — see the flow map in §5.

7 · The contrastive projection — training wheels ~328K

Plain: a two-layer network that squeezes the dossier into a 256-dim "comparison space" where cosine similarity is measured. It exists only for the training game below and is never used at inference.

The game (InfoNCE): take a comment + its real previous comment → that pair's representations should be similar. Take the same comment + a random previous comment (sampled from the dataset's context pool, re-shuffled every epoch with a seeded RNG) → should be dissimilar. The anchor is the comment alone; candidates are comment-with-context.

L = −log [ exp(sim(a,p⁺)/τ) / ( exp(sim(a,p⁺)/τ) + Σᵢ exp(sim(a,nᵢ)/τ) ) ] τ = 0.07

What this buys, in plain terms: it teaches the interaction module that which previous comment you attach matters — the representation for "They should all be kicked out" must change depending on whether the previous comment was about immigrants or about chess (same witness statement, two different lineups — the detective must notice which lineup it belongs to).

Why a separate projection at all? Standard practice (SimCLR etc.): let the comparison game reshape its own small space, and shield the main 1,024-dim dossier from being distorted by it. The task heads keep their workspace; the game gets its own room.

5Who trains whom — the gradient flow map

In plain English: after every prediction, the teacher (loss) sends a "you got this wrong by this much" signal backwards through the network — and every dial the signal passes through gets nudged. So the real question is: for each teacher, which components are standing in the signal's path? That's this section.
Teacher (loss)BERT encoderInteractionHate headTarget headReason headEvidence headContrastive proj.
hate (CE)✔ flows through✔✔ learns————
target (CE)✔✔—✔ learns———
reason (CE)✔✔——✔ learns——
evidence (BCE)✔ (token states)✘ bypasses it———✔ learns—
contrastive (InfoNCE)✔✔————✔ learns

Three consequences worth internalizing:

  • The trunk learns a blend of everything. BERT sits upstream of all six signals, so its dials are nudged by every active teacher. That's multi-task learning happening in the weights, not in a meta-algorithm.
  • The evidence head is a parallel branch. It tunes BERT's token-level representations without touching the interaction module or the verdict heads — supervision that can't interfere with the classification path.
  • The contrastive game shapes the shared dossier but never the verdicts directly. Its signal stops at the projection + interaction + encoder; the heads only feel it indirectly, through a better-traveled trunk.

6The loss system — one report card, five graded subjects

In plain English: training is grading. Every batch of examples gets five possible grades — one per subject (task). Subjects with no answer sheet in that batch are marked excused, not zero. The final grade is a weighted average, and only the final grade adjusts the dials. Missing data never masquerades as a wrong answer.
L_total = λ_hate·L_hate + λ_target·L_target + λ_reason·L_reason + λ_contrastive·L_contrastive + λ_evidence·L_evidence
Rule (from training/losses.py)Plain meaning
Missing label = -100 (IGNORE_INDEX)The collator writes −100 wherever a dataset has no label; cross-entropy's ignore_index skips exactly those rows. An unanswered question is skipped, not marked wrong.
A loss with zero valid rows returns NoneIt's simply not added to the total for that batch. No gradient, no fake signal.
Weights λ (default: hate 1.0, target 1.0, reason 1.0, contrastive 0.5, evidence 1.0)Loudness dials for each teacher. Contrastive is deliberately quieter — it's a shaping signal, not the main objective.
Every component logged per epochThe training summary records each subject's average grade separately, so you can see what improved, not just the total.
Classification = cross-entropy; evidence = binary cross-entropyCE grades "pick one of K answers"; BCE grades thousands of tiny yes/no highlight decisions (one per token).

7.3 · Batching: the collators (datasets/collator.py)

  • MultitaskCollator — the prep cook. Tokenizes each batch's comments (current + context), pads them to equal length, and writes the label tensors with -100 wherever a label is missing. For evidence training, it aligns word-level highlights onto subword tokens (if annotators highlighted "immigrants", the subword pieces "immi" + "##grants" inherit the highlight).
  • ContrastivePairCollator — wraps the above and adds the contrastive game pieces: each example's real context (positive) plus a randomly drawn context from the dataset pool (negative), re-sampled per epoch with seed + epoch so experiments stay reproducible. Rows with no context are flagged contrastive_active: false and excused from the game.

8Inside the training loop (training/trainer.py)

In plain English: one epoch = show the model every training example once, grade it, nudge the dials. The trainer's craft is in the safety rails that keep those nudges useful and repeatable. After each epoch it saves its full state — brain and diary — so a crashed run resumes instead of restarting.

Why trained_heads is the checkpoint's moral compass

The trainer records which heads actually received real labels during the run. The serving layer later refuses to answer for any head not on that list (*_available: false). So "we never trained this on fabricated data" isn't a policy promise — it's a bit-flag riding along with the weights.

9The reasoning layer — explains, never learns

In plain English: once the model has given a verdict, this layer answers "which words, and how do they connect?" — using two fixed tools: an x-ray (Integrated Gradients) and a referencing rulebook (the pronoun analysis). Neither tool contains a single learnable dial, and neither can invent text. If the tools can't find anything, the response says so.

9.1 · Integrated Gradients — the x-ray (reasoning/attribution.py)

The question: how much did each word push the verdict toward, say, "hate"?

The trick, plainly: start from a blank input (the padding embedding), and slowly replay the real sentence in ~32 tiny steps. At each step, ask "if I wiggle this word's numbers a little, how much does the hate score move?" Average those sensitivities, multiply by how far each word travelled from blank — that's the word's contribution.

IGᵢ = (xᵢ − baselineᵢ) × (1/steps) Σₖ ∂F(baseline + αₖ·(x − baseline))/∂xᵢ

Gradients flow only into the input embeddings — the model itself is untouched. Each word gets a signed score: positive = pushed toward the verdict. gradient_x_input (1 step) is the cheap, noisier alternative, selectable via config.

9.2 · From scores to highlights (reasoning/evidence_extractor.py)

per-token scores → drop zeros → keep tokens ≥ 15% of the strongest →
glue adjacent tokens → decode subwords back into real words →
top-5 spans, each with text + score + char offsets (start, end) + token indices

Every span is copied verbatim from the input with exact character offsets — that's what lets the frontend highlight the precise words, reliably, with no fuzzy matching.

9.3 · The reference analysis + templates (context_reasoner.py, reason_explainer.py)

  • Reference analysis: finds referring words in the current comment ("they", "them", "he"…) and links each to the phrase it points back to in the previous comment, with offsets on both sides: "They" (0–4) → "group of immigrants" (8–27). Explicitly labelled a heuristic (method: "deterministic evidence + context-reference analysis").
  • Templates: fixed sentence molds like "The current comment uses [X] to refer to [Y] … Strongest evidence: [Z]" — filled only with real predicted values. The system can say "I found no explicit reference relationship" — an honest abstention, never an invented target.
  • Graceful degradation: any crash in this layer still returns the classification, with "summary": "Reasoning unavailable." — reasoning never takes the classifier down (§1, principle 7).

10Serving — one brain, many requests (services/inference.py, main.py)

In plain English: the web server loads the model once at startup and keeps it in memory like a resident expert. Every HTTP request consults the same expert. Loading BERT per request would be like hiring a new surgeon for every patient.

10.1 · The lifecycle

uvicorn app.main:app
  └─ lifespan startup ──► InferenceService.load()
        ├─ MODEL_CHECKPOINT env set?        → load that exact file
        ├─ else checkpoints/default.json?   → load the file it points to
        ├─ else conventional paths?         → cc_context/best.pt → hx_full/best.pt → full/best.pt
        ├─ else                             → build an UNTRAINED model, report trained: false
        └─ load failure?                    → /health stays up; /predict & /explain return 503

10.2 · One request, end to end (POST /api/v1/predict)

  1. Validate — pydantic schema accepts both namings (text/context and current_comment/previous_comment), caps length at 5,000 chars, rejects blank text.
  2. Forward pass — tokenize, run the model once under torch.no_grad() (no learning, no memory of this request).
  3. Decode each trained head — softmax/sigmoid → label + confidence + full probability table.
  4. X-ray — Integrated Gradients over the current comment (gradients enabled only on input embeddings).
  5. Evidence spans — threshold, merge, decode, attach character offsets.
  6. Reasoning — reference analysis + templates; wrapped in try/except with an explicit fallback.
  7. Assemble — structured_explanation.build_explanation sets every *_available flag from reality, never from hope.

15"But why?" — the first-principles FAQ

Why use the [CLS] vector as "the meaning"?

BERT reserves its first input slot as a scratchpad that the layers train to fill with a whole-sentence summary (that's literally what it was pre-trained to do). It's a free, already-trained sentence summary — no extra machinery needed.

Why |E_c − E_p| AND E_c ⊙ E_p instead of just concatenating?

Concatenation says "here are two things" — the classifier must learn how to compare them. Difference says "here is where they disagree"; product says "here is where they agree". Handing the comparison pre-computed turns a hard learning problem into an easy one. Whether the shortcut actually helps is exactly what exp2-vs-exp3 measures.

Why is temperature 0.07 in InfoNCE?

Cosine similarities live in a narrow band (−1…1); dividing by a small τ stretches that band apart before softmax, so the loss can strongly punish confusing the real context with a random one (a magnifying glass over the score gap). Too small → unstable; too big → the game is too easy and teaches nothing. 0.07 is a well-tested default (SimCLR lineage).

Why is the IG baseline the PAD embedding (not zeros)?

IG needs a "meaningless input" to rewind to. Padding is the closest thing to "no word" that the model has actually seen in training — a fairer neutral point than an arbitrary all-zero vector the model may treat as alien.

Why −100 and not 0 for missing labels?

0 is a real class index ("the first label"). Using it would grade blank answers as "wrong class 0". −100 is outside every legal index, so ignore_index can skip it unambiguously — an excused absence, not a wrong answer.

Why macro-F1 for picking the best epoch?

Hate datasets are imbalanced — most comments are normal. Plain accuracy lets a lazy model score well by always saying "normal". Macro-F1 averages per-class F1 equally, so being good at the rare, important classes counts just as much.

Why does evidence come from IG instead of the evidence head?

Two different tools for two different jobs. The evidence head needs token-level training labels (only HateXplain has them) and learns one notion of "suspicious word". IG works on any trained model — including target/reason heads and Counter-Context models with no rationale data — and always explains this specific prediction. The head still exists for the comparison study (exp6) and for future speed-ups (its scores come free in one forward pass).

Why deterministic templates instead of an LLM writing the explanation?

Because the explanation is part of the evidence. If a language model composed it, you'd need another system to verify the verifier. With templates, every sentence is auditable: it can only contain the predicted label, the linked phrases, and the extracted spans — nothing else exists for it to say. Explainability you have to trust is not explainability.

Why keep the contrastive projection in the checkpoint if serving ignores it?

So training can resume exactly where it stopped (optimizer state and all), and so experiments can re-run the contrastive evaluation. Serving simply never calls it — the flag use_contrastive plus trained_heads make that unambiguous.
