Backend Architecture — explained from first principles

Context-Aware Hate Speech Detection with Structured Evidence-Based Reasoning · Python · FastAPI · PyTorch · Hugging Face Transformers

Everything here is written in plain language first, then the exact detail. Every number quoted below was measured from your code and your checkpoints in this repo — not estimated. Where a claim sounds surprising, there is a verification command right next to it.

How to read this

The single most useful mental model for this backend: it is two programs stapled together.

Program A — the factory (offline)

In scripts/, app/datasets/, app/training/, app/models/, app/evaluation/.

Downloads data → cleans it → teaches a neural network → writes a file of learned numbers (best.pt). Runs on your laptop / a GPU box. Slow, heavy, run once in a while.

Program B — the shop counter (online)

In app/main.py, app/api/, app/services/, app/reasoning/.

A web server. It loads the numbers from Program A once at boot, then answers POST /api/v1/predict in milliseconds. It never trains, never downloads anything, and never writes files.

The bridge between them is a checkpoint — one file that contains both the learned numbers and a written description of how the network was built, so the server can rebuild the exact same shape before loading the numbers.

If you understand that sentence, you already understand 70% of this codebase.

1What the system is asked to do

The user types a comment and (optionally) the comment that came before it. The backend must answer five questions with one request:

Question in plain EnglishField in the JSONWho produces it
Is this comment hateful, offensive, or normal?predictiontrained hate head
Who or what group does it target?targettrained target head
What kind of harm is it? (insult, threat, exclusion…)reasontrained reason head
Which exact words drove that decision?evidence[].textIntegrated Gradients (maths on the model, not a second model)
Did the previous comment change anything, and how?reasoning, context_useddeterministic pronoun→antecedent heuristic + templates
The design rule that shapes the whole backend: if a head was never trained, the API returns null and "reason_available": false. It does not guess, and it does not write a plausible-sounding explanation for a prediction it never made. This "no fabrication" rule is why so many flags like *_available exist in the code.

2First principle: what BERT actually gives you

Forget the hype. BERT is a fixed-size box of learned arithmetic. You feed it a sentence, you get numbers out. That is the entire contract.

  "They should all be kicked out ."
        │
        │  (1) split into word-pieces      ["[CLS]", "they", "should", "all", "be",
        │                                   "kicked", "out", ".", "[SEP]"]
        │  (2) each piece → a 768-number vector (a "meaning fingerprint")
        │  (3) let every piece look at every other piece, 12 times over (attention)
        ▼
  output, same length as input, each vector now CONTEXT-AWARE:
        [CLS] → [0.12, -0.87, ... ]  ┐
        they  → [0.04,  0.31, ... ]  │  each is 768 numbers
        ...                          ├─ 768-dimensional hidden states
        [SEP] → [0.00,  0.00, ... ]  ┘

  TWO things we use out of that:
    • [CLS] vector  = a single "fingerprint of the whole sentence"      (E_c, E_p)
    • per-token vectors = "fingerprint of each word given the others"   (for evidence)

Why the [CLS] vector and not the average of all tokens? Because BERT is pretrained so that [CLS] summarises the whole sentence for sentence-level tasks. It is the purpose-built summary slot.

The key insight that makes this project work: the word "kicked" gets a different 768-number vector depending on the words around it. That is the literal mechanism by which "did the previous comment change the meaning?" becomes computable — the numbers move.

Where: app/models/bert_encoder.py — a thin wrapper around transformers.AutoModel. It adds exactly one thing of its own: freezing control.

freeze_modePlain EnglishWhy you'd choose it
fullRepaint the whole networkBest accuracy, slowest, most memory. Default.
frozenNever touch BERT; only train your small headsTiny GPU, quick experiments. BERT is already good at English.
partialFreeze the bottom N layers, fine-tune the topThe classic middle ground. Bottom layers learn basic grammar, top layers learn task specifics.

3Why one encoder for two texts (weight sharing)

Naive approach: two separate models, one for the comment, one for the context. This code does not do that. It runs the same BERT twice.

              ┌──────────────────────────────┐
   comment ──►│                              │──► E_c   (768 numbers)
              │   ONE set of BERT weights    │
   context ──►│   (the exact same weights)   │──► E_p   (768 numbers)
              └──────────────────────────────┘
Analogy: imagine one translator who reads both the previous line of dialogue and the current line, and reports what each means. If you used two different translators with different vocabularies, comparing their answers would be meaningless — they might use different numbers for the same idea.

Because E_c and E_p come out of the same box, they live in the same coordinate system. So subtraction and multiplication between them are meaningful operations. That is the entire justification for the next section.

Notice also: the model still works without context. If no context is given, E_p is left as None and the interaction layer substitutes a vector of zeros (see context_interaction.py, forward()). Simpler than dragging a flag through the whole network, and it keeps the door open for "N previous comments" later.

Implementation detail worth knowing: in training, whole batches are padded, so rows without context would otherwise get a real but meaningless E_p from an empty pad string. The collator therefore emits a context_present mask of 1.0/0.0 which multiplies E_p — zeroing exactly the rows with no context (full_model.py, encode_pair).

4The interaction block: how two fingerprints become one

Now you have two 768-number fingerprints. You need one. Concatenating alone would be lazy — the model would have to figure out the relationship itself. So the architecture hands it two pre-computed relationship features.

D = |E_c − E_p| ← "how far apart are the two meanings?" (absolute difference) M = E_c ⊙ E_p ← "where do they agree?" (element-wise product) E_int = [ E_c ; E_p ; D ; M ] → 4 × 768 = 3072 numbers final = Dropout( GELU( Linear(3072 → 1024) ) ) → 1024 numbers
PieceLayman meaningSize
E_c"What this comment means"768
E_p"What the previous comment means"768
D"Where the two meanings differ"768
M"Where the two meanings reinforce each other"768
one linear layer squashes 3072 → 1024= 1024

Real numbers from your trained checkpoint: the projection matrix is 1024 × 3072 and a bias of 1024 — that is 3,146,752 parameters, the single biggest trainable block in the model after BERT itself.

Two modes exist purely so the ablation study has something to compare against:

  • mlp — the full [E_c; E_p; D; M]. The proposed model.
  • simple — just [E_c; E_p], no engineered D/M. This is the control that answers "did D and M actually help?"

Where: app/models/context_interaction.py — 83 lines, and compute_interaction_components() is a pure function you can unit-test in isolation (and they do — tests/test_interaction.py).

5The four heads: one shared understanding, four questions

A "head" here means one small linear layer glued on top of the shared understanding. The heavy lifting is shared; only the last layer is task-specific.

                    final representation  (1024 numbers)
                              │
     ┌──────────────┬─────────┴─────────┬──────────────────────┐
     ▼              ▼                   ▼                      ▼
  HATE HEAD     TARGET HEAD        REASON HEAD          EVIDENCE HEAD
  1024→3        1024→9             1024→8               per-token
  hate /        race / religion /  insult / threat /    is this word
  offensive /   gender / ...       exclusion / ...      part of the
  normal        + "none"           + "other"            justification?
                                                     (uses token vectors,
                                                      NOT the 1024 vector)

Hate head — hate_head.py

Three-way softmax: hate / offensive / normal (HateXplain's label set). There is a binary mode too, but it must be explicitly configured. Multiclass labels are never silently collapsed into binary — that would be a quiet lie about what the data says.

Target head — target_head.py

Nine-way softmax over protected-group categories, including an explicit none. Trained only where the dataset actually annotates targets (HateXplain does). The conversion from a dataset's own weird community names into these nine canonical buckets lives separately in app/datasets/label_mapping.py, so the model never sees raw dataset quirks.

Reason head — reason_head.py

The head always exists in the architecture, but it is trained only when real reason annotations exist. Never on guessed labels, never as a keyword list. This is the honest way to leave room for a feature you have not been given the data for yet — the frontend just hides the section until reason_available turns true.

Evidence head — evidence_head.py

Completely different from the other three. It does not use the 1024-number sentence vector. It takes the per-token vectors (768 each) and asks "is this word part of the justification?" — a yes/no decision for every token. It is trained with binary cross-entropy against HateXplain's human-highlighted rationales.

Do not confuse these two techniques — the repo is careful to keep them apart.

6The multi-task loss, and why missing data does not lie

Training is a game: the model predicts, you measure how wrong it was, you nudge the numbers. "How wrong" is the loss. With four heads you get four losses, so you add them up with weights:

L_total = λ_hate·L_hate + λ_target·L_target + λ_reason·L_reason + λ_contrastive·L_contrastive + λ_evidence·L_evidence defaults: 1.0 1.0 1.0 0.5 1.0

Now the problem: not every example has every label. HateXplain has no reason labels. Counter Context has neither target nor reason labels. If you "helpfully" filled those in with zeros, you would be teaching the model that everything is class 0.

The trick: missing labels are stored as the special number -100 (IGNORE_INDEX). PyTorch's cross-entropy understands -100 as "skip this row entirely". And if every row in a batch is -100, the loss function returns None and the component is dropped from the sum completely.

So on a Counter-Context batch, target_loss does not exist and is not added. The model is never punished for a question it was not asked.

A pleasant side effect: the trainer records trained_heads by observing which loss components actually fired. That set is written into the checkpoint and read back by the API — the API's *_available flags are literally derived from what got trained during the run. Nothing is hand-maintained, so nothing can drift.

Where: app/training/losses.py — _masked_cross_entropy, _masked_bce, compute_task_losses, combine_losses.

7Contrastive learning: teaching the model that context matters

Here is the subtle problem with just concatenating context: the network can cheerfully ignore E_p and still score well, because the current comment alone often predicts the label fine. You need a training signal that punishment-follows-ignoring-context.

The idea, in plain English:

  • Take a comment C and its real preceding comment P1. Good model: interaction(C, P1) should look similar to interaction(C, nothing) — same underlying meaning, enriched.
  • Now staple C to a wrong, randomly picked comment P2 (a "negative", sampled from a pool of all contexts). The representation should look different from the anchor.
  • Score = cosine similarity. Train so the true pairing wins over the false pairing.
L = −log exp(sim(anchor, positive)/τ) / ( exp(sim(anchor, positive)/τ) + Σᵢ exp(sim(anchor, negativeᵢ)/τ) ) τ (temperature) = 0.07 ← low value = sharper, harsher penalty for losing
Consequence of that low temperature: a comment is scored against only a few wrong contexts (1 by default, and the pair collator only does so when contexts exist). InfoNCE normally reaps its power from having many negatives. With one, the signal is weak — see gaps.

Contrastive learning is training-only. At inference the code does not build an anchor, a positive, or a negative. It just runs the context-aware path once. The projection layer sits unused in the served checkpoint (still ~130 K wasted parameters — see gaps).

Where: app/models/contrastive.py (projection + InfoNCELoss), app/training/contrastive_loss.py (glue to a batch), app/datasets/collator.py → ContrastivePairCollator (samples the negatives).

8Data layer: two datasets, one shape, zero silent guessing

You have two corpora that were built for different purposes. Merging them at the raw level would be a mess. Instead, each gets its own adapter, and both emit the same dataclass.

{
  "id": "cc-train-0",
  "current_text": ">The ~~UK~~ world is fucked  FTFY",
  "context_text": "The UK is fucked.",
  "hate_label": "neither",

Three honesty traps the code deliberately avoids.
  1. target_label: null means "we were not told". It does not mean "none", which means "we were told: no target". Conflating them would train the model on false negatives.
  2. Unmapped community names are preserved in metadata rather than force-fitted into a canonical bucket. Nothing is guessed.
  3. The Counter Context corpus has an infuriating naming quirk: target is the current comment and context is the preceding comment — target has nothing to do with target groups. Your adapter documents this inline and even writes the warning into every row's metadata.

Supporting pieces: preprocessing.py (normalisation), label_mapping.py (dataset labels → canonical), tokenizer.py (word-level rationales → subword alignment + character offsets), reason_import.py (your own annotation files → training rows), unified.py (the dataclass).

9The training pipeline, step by step

  python scripts/train.py --config cc_context
       │
       ├─ 1. read configs/base.yaml, then merge configs/cc_context.yaml on top
       │     (that is why every experiment file is 15 lines instead of 200)
       ├─ 2. pick a device: auto → CUDA if present, else CPU
       ├─ 3. set_seed(42) → python, numpy, torch, CUDA all seeded. Reproducible.
       ├─ 4. load the processed JSONL splits
       ├─ 5. build_label_maps()  label name → class index, per head
       ├─ 6. build_model():  BertEncoder.from_pretrained → FullModel(...)
       │     and produce model_kwargs — the BLUEPRINT we will save later
       ├─ 7. Trainer = optimizer(AdamW) + scheduler(warmup→decay)
       │                + collator(+contrastive wrapper) + dataloaders
       │                + AMP scaler (CUDA only) + early-stopping counter
       │
       └─ 8. for each epoch:
              ▲── shuffle, build batches
              │   forward pass
              │   compute only the losses that have labels
              │   backward, accumulate gradients (grad_accum_steps)
              │   clip gradients to max_grad_norm   ← stops one wild batch wrecking the run
              │   optimizer step, scheduler step
              │
              ├── evaluate on validation → macro-F1
              ├── write last.pt ALWAYS
              ├── write best.pt when macro-F1 improves
              └── stop early if no improvement for `early_stopping_patience` epochs

Every knob lives in YAML, never in the model classes: learning rate, batch size, warmup ratio, gradient accumulation, mixed precision, early stopping patience, loss weights, contrastive temperature. That separation is what makes the six-experiment ablation study possible without touching a line of Python.

Where: app/training/trainer.py (537 lines — the biggest file, and deliberately so: the loop, checkpointing and metrics are one honest unit), app/training/configs.py (YAML → dataclass), scripts/train.py (90 lines of CLI).

10Checkpoints: the bridge between the two programs

A checkpoint is not just weights. Look at what save_checkpoint() writes:

KeyWhat it isWho needs it
model_kwargsThe blueprint: architecture, label lists, which components are on, hidden sizesServing — to rebuild the identical shell
model_state207 tensors, ~113 M numbers of learned valuesServing
trained_headsWhich heads actually got trained, e.g. ["hate"]Serving — drives the *_available flags
config, metrics, epochHyperparameters and scoresHumans, reports
optimizer_state, scheduler_stateMomentum and learning-rate positionTraining only — to resume exactly
Plain-English version: the optimizer state is like a car's current speed and gear. To continue driving you need it. To just park the car in a showroom (serve predictions) you do not. So serving exports drop it.

scripts/export_serving_checkpoint.py writes a lean copy without those two keys — about 65% smaller — plus a serving_export note recording where it came from and when. That is what you ship to a container.

Loading is the mirror image, and it is carefully lazy in two ways:

  • All the heavy imports (torch, transformers, model classes) happen inside functions, not at module top. So importing the app for a unit test does not cost you a 500 MB model load.
  • The served bundle is a @lru_cache singleton built at FastAPI startup (the lifespan hook in main.py). BERT is loaded once per process, never per request.
  checkpoints/
  ├── default.json          {"checkpoint": "checkpoints/cc_context/best.pt"}
  │                          ← a pointer file. Edit this one line to swap the served model.
  ├── cc_context/
  │   ├── best.pt           epoch 2, macro-F1 0.566   ← currently served
  │   ├── last.pt           epoch 3
  │   └── training_summary.json
  └── hx_full/ ...

Resolution order at startup: MODEL_CHECKPOINT env var → default.json pointer → conventional paths (cc_context/best.pt, hx_full/best.pt, full/best.pt) → if nothing is found, build an untrained model and report every head as unavailable.

11Evidence: how the model shows its work (Integrated Gradients)

This is the best idea in the project, and the one worth understanding most deeply.

The question: the model said "hate". Which words caused that?

The naive trick: run the model, look at which input numbers the output depends on most — the gradient. But gradients are noisy: a word with a big gradient might have been sitting at a nearly-zero value anyway, so its actual influence on the answer was tiny.

Integrated Gradients (Sundararajan et al., 2017) fixes this by averaging over a path instead of looking at one point:

1. Take the input's number-vectors, and a "baseline" — here, the PAD embedding (i.e. nothing). 2. Walk a straight line from baseline to the real input, in small steps (default 32). 3. At each step, ask "how sensitive is the output to each word now?" 4. Average those sensitivities, then multiply by (real_input − baseline). Result: one signed score per token. Big positive = this word pushed the answer UP.

Then the scores are turned into something a human can read, in four passes (app/reasoning/evidence_extractor.py):

  tokens + scores
        │
        ├─ 1. rank / threshold   → keep tokens scoring ≥ 0.15 × the strongest token
        │                          (a RELATIVE threshold — so it always finds *something*
        │                           even for a low-confidence prediction)
        ├─ 2. merge adjacent      → "be" + "kicked" becomes one phrase, not two
        ├─ 3. decode subwords     → "##ed" glued back onto the word it belongs to
        └─ 4. take top-k (5)      → readable spans, each a VERBATIM slice of the input

  every span carries:
    text, score, token indices,
    AND start/end character offsets into the original comment  ← this is what the
                                                                 frontend highlights
Why the character offsets matter so much: the frontend never has to re-tokenise or guess where a phrase sits in the string. It receives start/end and highlights exactly that range. That removes an entire class of mis-highlighting bugs — the ones you get from BERT's weird word-pieces drifting out of alignment with the visible text.

Two methods are available: integrated_gradients (default, 32 forward passes, better quality) and gradient_x_input (1 pass, cheaper, noisier — the single-point approximation IG is named after).

12The explanation layers: sentences from numbers, deterministically

You now have: a label, a target, a reason, and evidence spans. Someone still has to write the English. This project does it with template composition — no LLM anywhere.

Layer 1 — reason explanation reason_explainer.py

reason + target + evidence  →  { summary, details, grounded_in }

Three rules it follows, spelled out in the module docstring:

  • Deterministic — same inputs, same sentence, every time.
  • Grounded — only the predicted reason, target and extracted spans. It never adds outside knowledge.
  • Honest — it never claims to know the author's intent, and never claims the context caused the prediction. Context is only ever reported as "included in the analysis".

If the reason head is unavailable, reason_explanation is null. No summary is invented. Templates can be overridden without editing code by dropping a configs/reason_templates.yaml next to the others.

Layer 2 — context reasoning context_reasoner.py

This answers the question that makes the project interesting: why did the previous comment matter?

Its core is a deliberately small, auditable heuristic — not attention weights, not a second model, not an LLM:

  previous:  "I saw a group of immigrants downtown."
  current:   "They should all be kicked out."

  Step 1 — find the antecedent in the PREVIOUS comment:
           scan right-to-left for a plural noun  → "immigrants"
           widen leftwards over determiners / prepositions / quantity nouns
           → "a group of immigrants"
           then strip leading determiners         → "group of immigrants"

  Step 2 — find referring words in the CURRENT comment:
           "They" is in LINKABLE_PRONOUNS          → link it

  Step 3 — emit a link with offsets on BOTH sides:
           { from_text: "They", from_start: 0, from_end: 4,
             to_text:   "group of immigrants", to_start: 8, to_end: 27,
             pronoun:   "they", relation: "refers_to" }

The vocabulary is hand-curated: pronouns, determiners, prepositions, quantity nouns, common verbs (to avoid latching onto "says"), stopwords, and a list of words ending in "s" that are not plurals (bus, news, always…). Everything is inspectable.

Then it composes the summary from fixed templates, keyed by the tone of the predicted label (hate-like / offensive / counter / neutral). And — this is the part that shows real engineering maturity — it has an abstention path:

When no reference relationship can be established, the summary says so: "The previous comment was included in the analysis, but no explicit reference relationship between the two comments was identified." A model that always produces confident reasoning is a model you cannot trust.

And robustness: the whole layer is wrapped in a try/except in inference.py. If reasoning crashes, the classification still returns — the reasoning block degrades to "Reasoning unavailable." A presentation layer must never be able to fail the prediction.

  "evidence": [ { "text": "kicked out", "score": 0.82,
                  "start": 20, "end": 30, "token_start": 5, "token_end": 6 } ],
  "reason_explanation": null,             ← null because the reason head is untrained
  "reasoning": { "summary": "...", "links": [...], "evidence": [...] },
  "context_used": true,
  "evidence_available": true
}

Because every optional section carries its own *_available flag, the frontend can render a section only when it is real — and show an explanation when it is not. "Unavailable" and "absent" are never the same thing.

14What actually happens during one request

  POST /api/v1/predict  {"text": "...", "context": "..."}
        │
   1.   Pydantic validates the shape (length, aliases, non-blank)
        │
   2.   get_inference_service()  →  the cached singleton (model already in memory)
        │
   3.   tokenize the current comment (and the context if present)
        │
   4.   ONE forward pass (no_grad):
        │      shared BERT(current)  → E_c
        │      shared BERT(context)  → E_p        ← only if context was supplied
        │      D, M, [E_c;E_p;D;M] → 1024-vector
        │      hate / target / reason head → logits  →  softmax  →  label + confidence
        │      (for each head that is in trained_heads; others are skipped entirely)
        │
   5.   Integrated Gradients over the same model, 32 steps
        │      → per-token scores → threshold → merge → decode → top-5 spans
        │      → character offsets for the frontend
        │
   6.   deterministic explanation templates
        │      reason + target + evidence  →  summary/details
        │      pronoun→antecedent heuristic → links → context summary
        │
   7.   build_explanation() assembles one dict, setting the *_available flags
        │
   8.   PredictResponse (Pydantic) serialises → JSON

  Total: ms on GPU, tens-to-hundreds of ms on CPU (the IG loop dominates).
Two things worth knowing about this path.
  1. The endpoint is declared def predict(...), not async def. FastAPI runs it in a threadpool, which is good here: a blocking PyTorch forward pass would otherwise freeze the event loop.
  2. But get_inference_service() is a process-wide singleton with a mutable _bundle, and nothing serialises access. Two concurrent requests both call model.eval() and share tensors. In practice fine for a research prototype; it is a real design decision to be aware of, not an accident. See gaps.

15Config and dependencies

There are two config systems, and keeping them separate is deliberate:

Runtime — .env → Settings

Encoder name, checkpoint path, device, max sequence length, label lists, loss weights, IG steps and threshold, CORS, log level.

Loaded by pydantic-settings, cached with @lru_cache so it is parsed once per process. "Nothing in the codebase should hardcode model names, dimensions, thresholds or paths."

Training — configs/*.yaml → TrainConfig

Epochs, LR, batch size, warmup, gradient accumulation, AMP, early stopping, component on/off switches, dataset files, label maps.

Merged with deep_merge(base, override). That is why cc_context.yaml is 15 lines and not 200.

18Learnables: only 1.4 million of the 113 million are yours

This is the headline number of the whole architecture, and it is easy to miss.

207 tensors, 112.96 M params

~111.5 M — frozen knowledge

The pretrained BERT weights. In freeze_mode: full these are trained, but the point stands: 98.5% of the parameter count is "the English language model", not "your idea".

~3.15 M — the interaction layer

One Linear(3072 → 1024). The largest trainable block you actually designed.

~0.13 M — everything else

All four heads, plus the contrastive projection. In your served checkpoint that is hate_head 3×1024 plus bias, and junk weights for the heads that were switched off.

And here is the design consequence, stated plainly:

Verify it yourself — the heads that were switched off are not merely "untrained", they are absent from the checkpoint. 
model_kwargs: architecture='full', use_context=True, use_contrastive=True,
              use_target=False, use_reason=False, use_evidence=False

Why this is a good architecture decision, in layman terms: turning off a component leaves a visible hole rather than a random-weight stub. A random-weight head would happily output a confident-looking label. Because the head does not exist, the code cannot even ask it for one — so target_available: false is a structurally guaranteed truth, not a promise someone has to remember to keep.

20The concepts you need, in plain English

TermOne-paragraph explanation
Pretrained / fine-tuning BERT already read a huge amount of English and learned general grammar and meaning. "Fine-tuning" means you start from that and nudge it on your task. It is the difference between teaching someone a new subject versus teaching them to read.
Token / word-piece BERT does not read whole words. It splits text into chunks. "kicked" might be one piece; a rare word gets chopped into pieces like immigr + ##ants. The ## means "glue me onto the previous piece". That is why the evidence extractor has to decode pieces back into readable phrases.
Embedding A sentence or word turned into a list of numbers (here, 768 of them) such that similar meanings land near each other. Everything the model "thinks" is a vector of these.
[CLS] A fake token prepended to every input. BERT is trained so its output vector summarises the whole sentence. We use it as the sentence fingerprint.
Head The small final layer that turns the shared understanding into one specific answer. "One body, four mouths."
Logits / softmax Raw scores out of a head (could be 3.2, -1.1, 0.4). Softmax squeezes them into probabilities that sum to 1 (0.93, 0.02, 0.05).
Loss A single number measuring how wrong the prediction was. Training = repeatedly nudging parameters to make it smaller.
Epoch / batch / step Batch = a handful of examples processed together. Epoch = one full pass over the training data. Step = one parameter update.
Gradient "If I nudge this parameter, which way does the loss move, and how much?" Training is just following gradients downhill.
Integrated Gradients An attribution method that measures how much each input word contributed to the output, by averaging gradients along a path from "no input" to the real input. More reliable than a single raw gradient.
Contrastive / InfoNCE Training by comparison. Make the correct pairing score higher than wrong pairings. Used here to force the model to actually use context.
Freezing Marking certain weights as not-trainable, so they stay exactly as pretrained. Saves time and memory, and prevents a small dataset from wrecking good pretrained knowledge.
AMP (mixed precision) Doing most arithmetic in 16-bit instead of 32-bit floats. Roughly 2× faster and less memory-hungry on modern GPUs. Automatically CPU-disabled here.
Gradient accumulation If you cannot fit a big batch in memory, process several small batches and only update after collecting all their gradients. Same effect as a big batch, less memory.
Gradient clipping Capping the size of gradients so one weird batch cannot blow up the whole run.
Ablation Systematically removing one part at a time to prove it actually helps. The difference between "we added contrastive learning" and "we can show contrastive learning contributed +X".
Checkpoint A saved file with all learned numbers plus enough metadata to rebuild the exact same network. The handoff from training to serving.
Post-hoc attribution Explaining a decision after it was made, by inspecting the model's maths — as opposed to a model that was built to explain itself. Honest, but it is a reconstruction, not a confession.

21Where it breaks: the honest list

You said you want this to be a solid project, so here is what is genuinely weak. These are findings, not opinions — each one is checkable.

real The evidence claims are only as good as hate

Attribution is computed only for the hate head (inference.py, target="hate" hard-coded in the call to compute_attributions). The /explain endpoint supports target and reason; /predict does not. So the highlighted words justify "hate/offensive/normal" and nothing else — while the UI may present them next to a target and reason label.

real The contrastive loss is decoration

  • negatives_per_anchor defaults to 1. InfoNCE's whole strength is having many negatives; with one it is closer to a coin flip.
  • The negative pool is every context string in the training set, chosen at random. A random preceding comment is usually trivially unrelated, so "tell these apart" is an easy task that teaches little.
  • Worse: the collator iterates the negative pool with a seeded random.Random while the DataLoader shuffles examples in parallel workers (collate_fn runs in worker processes). The sampling may not be reproducible in the way the code implies, and per-worker RNG state is not what you think it is.

real The interactive embedding path bypasses BERT's embeddings

Integrated Gradients needs to feed embeddings instead of token ids (you cannot interpolate integer ids). attribution.py therefore builds inputs_embeds itself and passes it through current_inputs_embeds.

But look at what that path skips: BERT's own embedding module also adds position embeddings and token-type embeddings. Whether those are re-applied on this path determines whether the attributions describe the same function the predictions came from. If they are not, the evidence is measuring a slightly different model than the one that produced the label — which would make the whole evidence section subtly unsound. This is the single most important thing to verify with a numeric test: run the same input both ways and check the predictions match.

real Dead computation in the hot path

Because the served checkpoint was built with use_target: false and use_reason: false, the model has no target or reason head — yet full_model.py computes a contrastive_projection(final_representation) on every forward pass, including inference, even though contrastive output is never used at serving time. That is wasted GPU work and ~328 K dead parameters in the shipped file.

real Real behavioural bugs in the serving layer

  • Untrained checkpoint + no context = 500. If context_input_ids is None but context_attention_mask was supplied, encode_pair calls self.encoder(input_ids=None, attention_mask=...) inside a try/except that only catches RuntimeError — so a ValueError escapes as a 500 instead of the intended 503.
  • model_info() is fragile. The error-reporting branch accesses bundle.model.hate_head unguarded. On BaselineModel that attribute is named classifier — so requesting status on a baseline-served deployment raises AttributeError (500) instead of returning info.
  • No timing in the API response. The frontend cannot show "analyzed in 340 ms" without it.

real The reason head has no validation signal

cc_reason.yaml keeps the standard validation split, and that split has no reason labels. So the reason head is trained but never validated. You cannot know whether it is learning anything. (The README admits this; it is still a gap.)

worth fixing Concurrency and deployment

  • Shared mutable singleton service, unsynchronised, with an assert in _require_bundle() — which is stripped out entirely under python -O.
  • CORS_ORIGINS=* by default. Fine for localhost, disqualifying for anything real.
  • No rate limiting, no request-size guard at the proxy layer, no auth. A public IG endpoint is an easy denial-of-service target: 32 forward passes per request.
  • Dockerfile installs torch with no CPU-only index — the image will be far larger than it needs to be. No healthcheck, no non-root user, no pinned versions.

worth fixing Data and reproducibility

  • The Counter Context numeric label order is explicitly flagged as unverified against the paper in base.yaml. If "0" is not actually hate speech, your headline model is trained on mislabelled data. Verify this before anything else.
  • Both datasets use random_split (see test_datasets.py) — random splits leak near-duplicate tweets between train and test, inflating metrics.
  • No dedup, no class-balance report, no input sanitisation beyond length and blank checks.

worth fixing The explanation layer can contradict the model

context_reasoner.py classifies tone with a hard-coded keyword set, including a small _POSITIVE_MARKERS list. The string these rules produce goes into the UI as the reasoning summary. So a keyword list — not the model — has the final word on how a decision is described. It is deterministic and documented, which is far better than an LLM, but it is still a second, unevaluated decision-maker sitting in front of your evaluated one.

worth fixing Honest numbers

Your served checkpoint's best validation macro-F1 is 0.566 over 3 classes (chance ≈ 0.33) — and it was selected at epoch 2 of 4, with validation loss rising from epoch 1 onward. That is overfitting on a small dataset, not a working detector. Any write-up should lead with this number, not the architecture diagram. The ablation.py module is exactly the right tool to show whether context and contrastive learning help — run it.

22How to make it solid (ordered by payoff)

#ActionWhy it mattersEffort
1 Write a parity test for the IG path. Same input, forward with input_ids vs forward with inputs_embeds; assert the argmax label and probabilities match to within tolerance. If this passes, your evidence section is sound. If it fails, you just found the bug that invalidates your main claim. Either way you learn something essential in an afternoon. Small
2 Verify the Counter Context label map against the NAACL 2022 paper, and write the verification (paper quote + date) into base.yaml. Cheapest possible fix for the biggest possible problem: silently mislabelled training data. Small
3 Replace random splits with the datasets' official splits (HateXplain ships post_id_divisions.json and your loader already reads it for the ids). Stops leakage between train and test. Your reported metrics become meaningful. Small
4 Fix the three serving bugs: guard encode_pair when context_input_ids is None; use getattr(model, "hate_head", None) or model.classifier in model_info(); catch Exception (not just RuntimeError) at the route boundary. Removes two guaranteed 500s from a deployed server. Small
5 Make the contrastive signal real. Raise negatives_per_anchor to 4–8, sample negatives from the same topic/label neighbourhood rather than globally at random, and move negative sampling into Dataset.__getitem__ with an explicit per-worker seed. Turns a mostly-decorative loss into a real inductive bias — the thing your whole "context matters" claim depends on. Medium
6 Add latency + version to every response (model_version, inference_ms, evidence_method). Makes production debugging and A/B comparison possible without a separate metrics stack. Small
7 Skip the contrastive projection when serving, and strip unused heads on export. Smaller checkpoint, less wasted compute per request. Purely additive to the export script you already have. Small
8 Annotate a validation split for reason labels (your annotation workspace already produces the format). Without it, the reason head is trained blind. With it, you can report macro-F1 and know whether to ship it. Medium (human time)
9 Split inference.py into model_loader.py + inference.py, and add a second, optional CLI wrapper (scripts/serve.py) that exercises the predict pipeline without HTTP. 10 Harden for deployment: pin versions, CPU-only torch in the Dockerfile, non-root user, /health healthcheck, a real CORS origin list, and a token-bucket limit on /predict. Turns "runs on my laptop" into "can be exposed". Medium
