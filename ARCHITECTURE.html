AIML Project · Backend Architecture Document

Context-Aware Hate Speech Detection

A multi-task NLP backend that classifies hate speech, identifies its target group and reason category, and generates attribution-based evidence spans — all from a single shared BERT encoder augmented with context interaction and contrastive learning.

FastAPI PyTorch HuggingFace Transformers Multi-task Learning Contrastive Learning Integrated Gradients HateXplain Dataset

Overview

The project is a production-ready FastAPI backend that wraps a custom PyTorch model. The model takes a current comment (and optionally a previous context comment) and produces four outputs simultaneously:

🎯 Hate Classification

Multiclass: hate / offensive / normal

Outputs a label, confidence score, and full probability distribution.

👤 Target Group

Who the speech is targeting — 9 categories including race, religion, gender, etc.

💬 Reason Category

Why it's hateful — 8 categories like insult, dehumanization, threat, etc.

🔍 Evidence Spans

Token-level attribution scores (Integrated Gradients) highlighting which words drove the prediction.

📌 Core Insight
The same BERT encoder is used (with shared weights) to encode both the current comment and the previous context. This is a deliberate design choice — weight sharing forces the model to learn a universal comment representation rather than two separate representations, and it reduces parameter count.

1. Shared BERT Encoder

File: app/models/bert_encoder.py — BertEncoder(nn.Module)

This is the backbone of the entire system. It wraps a HuggingFace AutoModel (defaulting to bert-base-uncased) and exposes two things from its forward pass:

  • last_hidden_state — shape [B, T, 768] — contextual token representations
  • cls — shape [B, 768] — the [CLS] token embedding, used as the sentence representation

Why Shared Weights?

The same BertEncoder instance encodes both the current comment and the previous context. This means there's only one BERT, not two. This is important:

  • Halves the parameter count compared to a dual-encoder approach
  • Forces a unified semantic space — both comment and context live in the same embedding geometry
  • Makes the contrastive objective work correctly (anchor, positive, negative must be in the same space)

Freeze Modes

ModeWhat freezesWhen to use
fullNothing — all BERT weights fine-tuneDefault; best accuracy if you have enough data
frozenAll BERT weights — only task heads trainVery small datasets; fast experiments
partialEmbeddings + bottom N layersMedium data; preserve low-level representations, fine-tune higher layers
📚 What to Learn Here
Transfer Learning: BERT was pre-trained on masked language modeling and next-sentence prediction on Wikipedia + BookCorpus. Fine-tuning means you start from these general language representations and adapt them to hate speech classification. The [CLS] token is specifically designed to carry a sentence-level summary — that's why it's used as the input to the classification heads. 
# How the encoder is called in full_model.py
def _encode_current(self, input_ids, attention_mask, ...):
    encoded = self.encoder(input_ids=input_ids, attention_mask=attention_mask)
    return encoded["cls"], encoded["last_hidden_state"]
    #          ↑ [B,768]      ↑ [B, seq_len, 768]

def _encode_context(self, context_input_ids, context_attention_mask):
    # SAME encoder — shared weights!
    return self.encoder(input_ids=context_input_ids, ...)["cls"]

2. Context Interaction Layer

File: app/models/context_interaction.py — ContextInteraction(nn.Module)

After encoding both comments, the interaction layer combines them into a single context-aware representation. This is where the real NLP insight lives.

The Math

Eint = [Ec ; Ep ; |Ec − Ep| ; Ec ⊙ Ep] → Linear(3072 → 1024) → GELU → Dropout
SymbolMeaningShapeWhy it's there
E_cCurrent comment CLS embedding[B, 768]What is being said right now
E_pPrevious context CLS embedding[B, 768]What was said before
D = |E_c − E_p|Absolute difference[B, 768]How much the two comments differ — captures contrast/shift in topic
M = E_c ⊙ E_pElement-wise product[B, 768]Where the two comments agree — captures shared semantic features

Concatenating all four gives a [B, 3072] vector which is then projected down to [B, 1024] via a linear layer + GELU activation.

Two Modes (for ablation)

mlp (proposed)

Uses all four components: [E_c; E_p; D; M]

Input dim: 4 × 768 = 3072

Captures both difference and similarity signals explicitly.

simple (ablation)

Only [E_c; E_p] — no engineered features

Input dim: 2 × 768 = 1536

Used in exp2 to test if D and M actually help.

📚 What to Learn Here
This is a classic Natural Language Inference (NLI) interaction pattern — the same [difference + product] feature engineering was used in InferSent and decomposable attention models before transformers dominated. The intuition: subtraction captures what's unique to each sentence, multiplication captures shared features. Applied here to hate-speech context: if the previous comment is sarcastic or inviting a specific slur, D and M will encode that relationship differently than mere concatenation. 
def compute_interaction_components(e_c, e_p):
    d = torch.abs(e_c - e_p)          # difference
    m = e_c * e_p                      # element-wise product
    return torch.cat([e_c, e_p, d, m], dim=-1)   # [B, 3072]

class ContextInteraction(nn.Module):
    def forward(self, e_c, e_p=None):
        if e_p is None:
            e_p = torch.zeros_like(e_c)   # graceful: no context = zero vector
        raw = compute_interaction_components(e_c, e_p)["concat"]
        return self.dropout(self.activation(self.projection(raw)))

3. Prediction Heads

All heads receive the same final_representation — the [B, 1024] vector output by the interaction layer — and independently classify it. This is the multi-task learning setup: one shared representation, multiple objectives.

HateHead

Task: Multiclass classification — hate / offensive / normal

Architecture: Linear(1024 → 3) + Softmax

Loss: Cross-entropy

Also supports binary mode (single logit + sigmoid) via config.

TargetHead

Task: Who is being targeted — 9 categories

Architecture: Linear(1024 → 9) + Softmax

Loss: Cross-entropy (only where annotations exist)

Trained only on datasets that provide target labels (HateXplain does).

ReasonHead

Task: Why it's hateful — 8 reason categories

Architecture: Linear(1024 → 8) + Softmax

Loss: Cross-entropy (only when reason annotations available)

Never trained on fabricated/keyword-inferred labels. Off by default.

EvidenceHead

Task: Per-token rationale binary classification

Architecture: Linear(768 → 1) over each token state

Loss: Binary cross-entropy (only on tokens with gold rationale labels)

Takes the token states [B, T, 768], not the CLS vector.

📚 What to Learn Here — Multi-Task Learning
Multi-task learning works by sharing a representation (the interaction output) across tasks. The intuition is that tasks like "is this hate speech?" and "who is targeted?" are related — learning them together should improve the shared representation because gradients from all tasks flow through the same BERT encoder. In practice, you need to balance the loss weights (λ values in the config) carefully so one task doesn't dominate.

4. Contrastive Learning (Training Only)

Files: app/models/contrastive.py, app/training/contrastive_loss.py

Contrastive learning is an auxiliary training objective that runs only during training (never at inference). It teaches the model that the context matters: the same comment paired with its correct preceding context should produce a representation that is close to the comment-only anchor, while pairing it with a wrong (contrasting) context should produce a distant representation.

InfoNCE Loss

LInfoNCE = −log [ exp(sim(a,p)/τ) / (exp(sim(a,p)/τ) + Σi exp(sim(a,ni)/τ)) ]
  • 1
    z_anchor Encode just the current comment, project through ContrastiveProjection → L2-normalized [B, 256]
  • 2
    z_positive Encode current comment + its CORRECT preceding context, project → [B, 256]
  • 3
    z_negative Encode current comment + a RANDOM contrasting context (different comment's context), project → [B, N, 256]
  • 4
    Loss Push z_positive close to z_anchor, push all z_negative away. Temperature τ=0.07 controls sharpness.
📚 What to Learn Here — InfoNCE / SimCLR-style Contrastive Loss
InfoNCE (from CPC, 2018) is the same family of losses used in CLIP and SimCLR. It's a cross-entropy over similarities — treat the positive pair as the "correct class" and all negatives as wrong classes. Temperature τ controls how peaked the distribution is: low τ = very sharp = harder training signal. The projection head (a small MLP that maps to a lower-dim space) is a key trick from SimCLR — the projection head is discarded after training; it prevents the contrastive objective from distorting the main representation space. 
# ContrastiveProjection: final_representation → contrastive space
class ContrastiveProjection(nn.Module):
    def __init__(self, input_dim, projection_dim=256):
        self.projection = nn.Sequential(
            nn.Linear(input_dim, projection_dim),
            nn.GELU(),
            nn.Linear(projection_dim, projection_dim),
        )
    def forward(self, features):
        return F.normalize(self.projection(features), dim=-1)  # L2-normalize!

5. Evidence Extraction & Attribution

Files: app/reasoning/attribution.py, app/reasoning/evidence_extractor.py

The project uses two distinct but related mechanisms for token-level explanations. It's critical to understand the difference:

🏋️ Supervised Rationale (Training)

EvidenceHead — a learned classifier over token states.

Trained against gold rationale annotations from HateXplain (which words human annotators marked).

This is a predictive head — it learns to predict where the hate signal is.

🔬 Post-Hoc Attribution (Inference)

Integrated Gradients — computed from model gradients, no extra training needed.

Asks: "how much does each input token contribute to the predicted class logit?"

This is an explanation method — it doesn't require annotations.

Integrated Gradients — How it Works

  • 1
    Define a baseline PAD token embeddings — the "absence of information" reference point
  • 2
    Interpolate Create N=32 steps from baseline embeddings to actual input embeddings: x(α) = baseline + α·(input − baseline), α ∈ {1/32, 2/32, …, 1}
  • 3
    Compute gradients At each step, run a forward pass and compute ∂(logit of target class)/∂(embedding) using autograd
  • 4
    Integrate Average the gradients across all 32 steps, then multiply by (input − baseline). Sum over the embedding dimension to get a scalar per token.
  • 5
    Extract spans Take the top-K tokens by attribution score, merge adjacent tokens into spans, filter by min_score threshold
📚 What to Learn Here — Integrated Gradients (Sundararajan et al., 2017)
IG satisfies the completeness axiom: the sum of all attribution scores equals F(input) − F(baseline). This means attributions are not arbitrary — they exactly account for the difference in model output between having the input vs. not. It's one of the gold-standard XAI methods for NLP. The cheaper alternative, gradient×input, is just the first step of IG (α=1 only) — faster but noisier.

Multi-Task Loss System

Ltotal = λhate·Lhate + λtarget·Ltarget + λreason·Lreason + λcontrastive·Lcontrastive + λevidence·Levidence

📌 Important Design Choice
A loss component is silently skipped (not zeroed out, but fully absent) when the batch has no ground truth for it. This means training on mixed datasets works correctly — you never have spurious gradients from labels that don't apply to a given example. The -100 ignore index is the standard PyTorch pattern for masked cross-entropy.

Trainer

File: app/training/trainer.py

Key Features

AMP (Automatic Mixed Precision)

Uses torch.autocast + GradScaler on CUDA.

Forward pass runs in float16; weights stay in float32. Roughly 2× speedup + halved GPU memory.

Gradient Accumulation

Simulates larger batch sizes by accumulating gradients over N steps before updating.

Useful when GPU memory limits real batch size to e.g. 8, but you want effective batch of 32.

Linear Warmup + Decay LR

LR ramps up linearly for warmup_ratio × total_steps steps, then decays linearly to 0.

Standard for fine-tuning BERT — prevents large gradient updates in early steps.

Early Stopping

Monitors macro_f1 on validation set. If no improvement for patience epochs, training stops.

Saves best.pt + last.pt checkpoints independently.

The model_kwargs dict in the checkpoint stores the exact architecture configuration (labels, interaction_dim, which heads are active, etc.) so inference can rebuild the exact same model structure without needing the original config file. The InferenceService class is the bridge between FastAPI routes and the ML model. It's a process-wide singleton (via @lru_cache) — the model loads once and stays in memory.

Prediction Pipeline (what happens on POST /predict)

  • 1
    Tokenize Current text + optional context → input_ids, attention_mask tensors (max 128 tokens each)
  • 2
    Forward pass (no_grad) Model produces hate_logits, target_logits, reason_logits, rationale_logits
  • 3
    Decode heads Softmax + argmax on each head's logits → label + confidence + full probability dict
  • 4
    Attribution (with grad) Run Integrated Gradients on the hate head → per-token scores → top-K evidence spans
  • 5
    Context reasoning Deterministic analysis of the relationship between current comment and context (no LLM generation)
  • 6
    Assemble response build_explanation() combines all outputs into the structured API response object

Key Design Decisions

Why not use a [SEP] separator and pass both comments as one sequence?

The standard BERT approach would concatenate current + context with a [SEP] token and let BERT attend across both. This project uses separate encodings instead because:

  • It enables the explicit D (difference) and M (product) features — impossible with joint encoding
  • It enables the contrastive objective, which needs separate representations
  • Longer sequences (>128 tokens for both comments combined) hit BERT's positional encoding limit
  • Ablations can isolate the contribution of context cleanly
Why not use attention weights for explanation instead of Integrated Gradients?

Attention weights are not faithful explanations — a head can attend to a token but have zero impact on the output (if the value vector gets cancelled or the next layer ignores it). IG is gradient-based and directly measures the actual impact on the predicted logit, satisfying formal axioms (completeness, sensitivity, implementation invariance).

Why is the contrastive projection head discarded at inference?

The projection head's job is to provide a "safe" space for the contrastive loss to operate in, so the loss doesn't directly distort the main representation space. At inference, you want the representation without the projection transform — the interaction output is a richer, higher-dimensional space than the 256-dim contrastive space. This pattern comes from SimCLR (Chen et al., 2020).

Why store model_kwargs in the checkpoint?

The architecture is fully configurable — heads can be enabled/disabled, interaction_dim varies, label sets change per dataset. Storing the exact config that built the model means you can reload any checkpoint on any machine without needing the original YAML config. The checkpoint is fully self-describing.
