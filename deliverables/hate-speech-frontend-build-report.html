01Outcome

The complete frontend is implemented, type-checked, built and served successfully. It pairs with the existing FastAPI backend (AIML_Project/backend) and renders the structured reasoning pipeline: prediction, confidence, target, reason, evidence spans and context usage.

The UI is a renderer of model results — it never classifies text, never infers reasons, and never generates explanations. Availability flags (reason_available, etc.) are respected: unavailable heads show explicit "Not available" states instead of fabricated output.

  • Done  Implementation — components, pages, API layer, store, utilities, configs.
  • Done  Type-check + production build pass (strict TypeScript).
  • Done  Preview server serves the built app (HTML + assets, HTTP 200).
  • Done  Cross-origin contract verified against the live backend (CORS preflight + POST).
Delivered via the native toolchain: the delegated executor (ZCode) failed at dispatch with a model-request error before any changes, and per its fallback contract the build was completed directly with full local verification.

04How to run

Port note (this machine): port 8000 is already occupied by a Windows portproxy (→ WSL), and the 4105–4204 range is reserved by Windows — so run the backend on 8001 and keep the frontend's .env in sync (already set to http://localhost:8001).
# 1) backend (from backend/)
uvicorn app.main:app --reload --port 8001

# 2) frontend (from frontend/)
npm install
npm run dev        # http://localhost:5173

Serve a trained model by pointing the backend at a checkpoint ($env:MODEL_CHECKPOINT="checkpoints\full\best.pt"). Without one, the UI renders in its "untrained model" state — every head reports Not available, honestly.

05UX contract highlights

  • Inputs — Conversation Context (optional) and Current Comment (required, char count, Ctrl/⌘+Enter, clear validation); demo fill-buttons are labeled as inputs only.
  • Results — Prediction card with semantic color + icon + label (never color alone); Target and Reason cards with explicit "Not available for this model" states; Reason notes it "requires a reason-annotated model".
  • Evidence (core feature) — the original comment with inline highlights; hover/focus/tap reveals the attribution score; offsets used when provided; repeated phrases handled left-to-right; partial mapping degrades gracefully to the ranked list.
  • Context — shows "Context used" only when the backend reports context_used; wording stays neutral ("Context was included in this analysis").
  • Model status — live from /health + /api/v1/model/info: device, trained state, per-head availability, backend online/offline.
  • Loading / errors — indeterminate animated state (no fake steps or percentages); errors mapped to the spec's messages (backend unavailable, timeout, validation, model unavailable).
  • History — localStorage; click an item to reopen a stored analysis; explicit "Clear history" with confirmation.

06Caveats & next steps

  • In-browser walkthrough not performed — type-check, build, preview and the CORS contract are verified; open the app once while the backend runs to eyeball the visuals.
  • Target / Reason / Evidence states depend on the served model — with a trained checkpoint they populate; because the runtime renders availability flags directly, this was exercised at the contract level, not per-head at runtime.
  • Evidence mapping is attribution-based display — offsets are not yet provided by the backend; the matcher handles this, and the types already accept start/end when it changes.
  • Demo buttons never fabricate results — they only fill the inputs.

Suggested next steps

  2. Train the model (python scripts\train.py --config full) and serve it to see populated reason/target/evidence panels.
  3. Optional polish: add per-token attribution view using /api/v1/explain (already typed in the API layer).
